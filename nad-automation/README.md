# NadBounty automation (Monad testnet and mainnet)

Isolated Linux runners use the published SDK 0.10.0 and explicit Monad deployments. `NAD_NETWORK` selects `monad-testnet` (the default) or `monad-mainnet`; any other value is refused, the adapter is pinned per network (testnet `0xf88B980B3AB1CD5A2Befd9c0B88B70196f215020`, mainnet `0x5C38F98Fb3F3BA3eB8206Cb653eeDC8C159E1bE4`) and so is the mirror (testnet `0x59e970574D9aDc30892d094C893DA4B73EBE40a0`, mainnet `0x05e17AaCBf7c8e47D4Db4B9108f66f846ceDdAC5`) and the reputation sync reads `config/testnet.json` or `config/mainnet.json` and checks the chain id, the mirror address, the relayer and that the mirror is owned by the Safe. The reputation wallet has only the Safe-approved mirror reporting role; the keeper has no roles and calls permissionless settlements after on-chain deadlines. Each write uses exact estimation, rounded +50%, fixed gas price, bounded spending, receipts and state readback.

`npm ci --ignore-scripts`, `npm run typecheck`, `npm test`. Set the dedicated runtime variables from the workflow, then `npm run keeper -- --broadcast` and `npm run sync -- --broadcast`. Both are read-only by default. Keys stay in encrypted Actions secrets; neither the deployer nor any Safe owner key is uploaded. Actions permissions are read-only, PR runs receive no live credentials, and the scheduled live job runs only the reviewed default branch.

Reputation comes from finalized raw ERC-8004 feedback, explicit Base/Arc writers and current same-block identity ownership. All previous recipients are reconstructed from mirror events plus a Redis write-ahead journal and durable cursor. Revocations/transfers produce changed or zero records. Identical existing values skip the transaction: the on-chain source block remains the last delivered snapshot; each run separately records its newly verified source blocks. This is a trusted relayer, not a DON attestation. Discovery fails above 2000 board jobs and needs the indexer at scale.

Separate Redis leases serialize both runners across hosts. If a receipt is uncertain, the runner reports its hash and fails; a later scan checks chain state before retrying. A concurrent keeper may safely lose an already settled candidate. No new contests are opened, and adapter pause is preserved. Testnet job 7 was settled by the keeper after its real deadline on 2026-10-10 (tx `0x112b4a4036ece28231d3a28827ecefedd2bd94edd2cdefacfab719b2d8c4107a`).

## Workflows

| Network | Workflow file | Schedule | Chain, relayer and signing secrets |
|---|---|---|---|
| Monad testnet (10143) | `.github/workflows/nadbounty-automation.yml` | minutes 7 and 37 of every hour, and manually | testnet relayer `0x77eDC6eCfa56019fD57deC360D8F3862c4D44226`; secrets prefixed `NAD_AUTOMATION_` |
| Monad mainnet (143) | `.github/workflows/nadbounty-mainnet-automation.yml` | minutes 12 and 42 of every hour, and manually | mainnet relayer `0x78B3D0e6703906be0509A4dE64f8a6010eeB6904`; separate signing secrets `NAD_MAINNET_REPUTATION_RELAYER_PRIVATE_KEY` and `NAD_MAINNET_KEEPER_PRIVATE_KEY` |

Each workflow runs the keeper and then the reputation sync. The mainnet workflow sets `NAD_NETWORK=monad-mainnet`, the adapter address and public Monad RPC URLs; the Redis lease store and the Base and Arc read RPCs are shared with testnet, the signing keys are not. Telegram reminders have their own workflows (`nadbounty-reminders.yml` for testnet, `nadbounty-mainnet-reminders.yml` for mainnet). The mainnet workflow and reminder files live on `main`; they are scheduled, and as of 2026-10-13 their recorded runs were manual dispatches (see `docs/security/NADBounty_V48_LAUNCH_READINESS.md`). The first mainnet reputation sync mirrored the Arc owner `0x092F4483526eBc2476c247cB88d166aDb7C3232f` as 6 paid jobs (score sum 535).

Budget caps are 0.15 MON per transaction, 0.5 MON per reputation run and 1 MON per keeper run, on both networks. Monitor the two dedicated balances per network; funding from the deployer is a separate local bounded operation and never part of the schedule. Mainnet signing keys are dedicated wallets, never the deployer or a Safe owner.
